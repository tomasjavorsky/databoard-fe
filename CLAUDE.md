## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — type-check (`tsc -b`) and build for production
- `npm run lint` — run ESLint
- `npm run preview` — preview the production build

There is no test suite configured in this repo.

## Environment

The app reads its backend URLs from Vite env vars (e.g. `.env.local`):

- `VITE_GRAPHQL_URL` — GraphQL endpoint, consumed in [src/lib/graphql-client.ts](src/lib/graphql-client.ts)
- `VITE_CHAT_URL` — chat SSE endpoint, consumed in [src/hooks/useChat.ts](src/hooks/useChat.ts)

Both point at the `databoard-be` server (see below).

## Architecture

This is a React 19 + TypeScript app built with Vite, using:

- **TanStack Router** for routing — routes live in `src/routes/` as files, and `src/routeTree.gen.ts` is generated by the `tanstackRouter` Vite plugin (`autoCodeSplitting: true`). Never hand-edit `routeTree.gen.ts`; add/change routes by editing files under `src/routes/` and letting the plugin regenerate it.
- **TanStack Query** for server state — a single `QueryClient` is created in [src/main.tsx](src/main.tsx). Data-fetching hooks (e.g. [src/hooks/useProducts.ts](src/hooks/useProducts.ts)) wrap `graphqlRequest` calls in `useQuery`.
- **A hand-rolled GraphQL client** ([src/lib/graphql-client.ts](src/lib/graphql-client.ts)) — a thin `fetch` wrapper, no codegen or Apollo/urql. Queries/mutations are inline template strings next to the hook that uses them.
- **shadcn/ui + Radix + Tailwind v4** for UI components ([components.json](components.json)), with the `@` path alias resolving to `src/` (configured in both [vite.config.ts](vite.config.ts) and `tsconfig`). Generated primitives live in `src/components/ui/`.

### Chat feature

[src/hooks/useChat.ts](src/hooks/useChat.ts) talks to the backend's `/chat` endpoint over a raw `fetch` + manually-parsed SSE stream (not `EventSource`, since it needs to POST a body). It handles `text` (streaming deltas), `tool_call`/`tool_result` (surfaced as `toolStatus`), `done`, and `error` events. When a `tool_result` for `update_product` succeeds, it invalidates the `['products']` query so the product table reflects the change made via chat.

## Backend (sibling repo)

This frontend talks to `databoard-be`, a sibling project in the same parent directory (`../databoard-be`). It is a separate Node/TypeScript repo, not part of this workspace:

- **Fastify** server ([src/index.ts](../databoard-be/src/index.ts)) exposing:
  - A **GraphQL API** (Mercurius, schema in `src/graphql/typeDefs.ts`) backed by **Postgres via Drizzle ORM** (`src/db/`) — this is the single source of truth for product data and the only thing with DB access.
  - A **`POST /chat` SSE endpoint** ([src/chat/chat.route.ts](../databoard-be/src/chat/chat.route.ts)) that drives an agentic loop against the Anthropic Messages API (`src/chat/chatService.ts`), streaming `text`/`tool_call`/`tool_result`/`done`/`error` events matching the shape `useChat` expects.
- An **MCP server** (`src/mcp/server.ts`, run via `npm run mcp` in that repo) exposing `list_products`, `get_product`, and `update_product` tools. It has no DB access of its own — every tool call is proxied through the GraphQL API, so GraphQL-side validation/logic applies uniformly whether a change comes from the UI or the chat agent.
- The backend's Fastify process spawns/connects to that MCP server over stdio as a long-lived subprocess (`src/mcp/client.ts`) and hands its tools to the Anthropic SDK during chat turns.

When a change spans both product behavior and chat/tool behavior, expect to touch both repos: the GraphQL schema/resolvers and DB schema live in `databoard-be`, while this repo only consumes the GraphQL API and renders chat output.
